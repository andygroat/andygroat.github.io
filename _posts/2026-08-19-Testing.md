## Intro

The initial version of the APIs had some basic functionality for creating, getting and completing todo items, before we go any further in building more functionality into the APIs, we will want to add testing.

In the classic repo, I will continue to use the libraries that I have traditionally used for testing - [NUnit](https://nunit.org/) and [NSubstitute](https://nsubstitute.github.io/).

In the VSA repo, I will use the new [TUnit](https://tunit.dev/) library.

The below comparison is high-level and focuses on the core functionality of libraries, for a complete migration guide, check out the [TUnit migration guide](https://tunit.dev/docs/migration/nunit).

## Library Overview

### NUnit

NUnit is unit-testing framework for .NET with over 679 million downloads on Nuget.  It uses attributes to mark test calsses and methods and includes built-in assertions to check if test results match the expected result for the test.

### NSubstitute

NSubstitute is mocking library with over 292 million downloads on Nuget. It creates substitutes for the types you need with a very simple `Substitute.For<>` syntax. There are other mocking libraries that could be used, such as Moq, however, NSubstitute has been a favourite of mine for many years due to its simplicity for setting up substitutes and then being able to assert calls to it.

### TUnit

TUnit is modern testing framework with performance in mind. This performance is what has got my attention as there has been may times when I have gotten slightly bored waiting for tests to run. How is TUnit more performant? It discovers tests at compile time rather than runtime reflection and it runs tests in parallel. If you want see how much faster TUnit be in comparison to the libraries you use, they have benchmarked TUnit against those, which can be found [here](https://tunit.dev/docs/benchmarks/).

## Syntax Comparison

The syntax between NUnit and TUnit are actually very similar, your test methods are marked with `[Test]` attribute. NUnit use to also require the `[TestFixture]` attribute on classes, but from version 2.5 this is now optional. Here is a basic example of the same test in NUnit and TUnit.

### NUnit Example

```c#
[TestFixture] // Optional after v2.5
public class CalculatorTests
{
    [Test]
    public void Add_ReturnsSum()
    {
        // Arrange
        var calculator = new Calculator();

        // Act
        var result = calculator.Add(2, 3);

        // Assert
        Assert.That(result, Is.EqualTo(5));
    }
}
```

### TUnit Example

```c#
public class CalculatorTests
{
    [Test]
    public async Task Add_ReturnsSum()
    {
        // Arrange
        var calculator = new Calculator();

        // Act
        var result = calculator.Add(2, 3);

        // Assert
        await Assert.That(result).IsEqualTo(5);
    }
}
```

Note in TUnit, it is recommended that the tests are `async Task` because the assertions return awaitable objects.

### Test Data

Both NUnit and TUnit provide attributes for passing data into test methods.  In NUnit this attribute is `[TestCase(arg1, arg2)]`, while in TUnit the attribute is `[Arguments(arg1, arg2)]`.  It should also be noted that the test in TUnit also requires the `[Test]` attribute, while NUnit does not.

### Test Setup & Tear Downs

In NUnit test fixtures can have setup and tear down methods that run before and after tests.  These methods are decorated with the `[Setup]` and `[TearDown]` attributes.

```c#
[SetUp]
public void SetUp()
{
    // Runs before the test, can be used to avoid repition of code, for example
    // when setting up the class to be tested
}

[TearDown]
public void TearDown()
{
    // Runs after the test, can be used to ensure resources are disposed correctly
    // after ther test is finished, for example, disposing of in-memory ef db contexts.
}
```

In TUnit, the setup and tear down methods are decorated with the `[Before(Test)]` and `[After(Test)]` attributes.

## Mocking

Mocking allows you to create a simulated or fake instance of a class which can then be used in tests to return specific data when methods are called. When testing with NUnit, I tend to use NSubstitute for mocking, but TUnit comes with its own mocking capabilities (TUnit.Mocks). Much like the tests above, mocking between NSubstitute and TUnit.Mocks is very similar, here is an example demonstrating.

### NSubstitute & NUnit Example

```c#
public interface ICalculator
{
    int Add(int x, int y);
}

public class CalculatorTests
{
    [Test]
    public async Task Add()
    {
        // Arrange
        var x = 2;
        var y = 3;

        var mock = NSubstitute.For<ICalculator>();

        // Expectations - Setup returns from mocks
        mock.Add(Any(), Any()).Returns(5);

        // Act
        ICalculator calculator = mock;
        var result = calculator.Add(x, y);

        // Assert
        await Assert.That(result, Is.EqualTo(5));
        mock.Received(1).Add(2, 3);
    }
}
```

### TUnit.Mocks Example

```c#
public interface ICalculator
{
    int Add(int x, int y);
}

public class CalculatorTests
{
    [Test]
    public async Task Add()
    {
        // Arrange
        var x = 2;
        var y = 3;

        var mock = ICalculator.Mock();

        // Expectations - Setup returns from mocks
        mock.Add(Any(), Any()).Returns(5);

        // Act
        ICalculator calculator = mock;
        var result = calculator.Add(x, y);

        // Assert
        await Assert.That(result).IsEqualTo(5);
        mock.Add(2, 3).WasCalled(Times.Once);
    }
}
```
